# 828 Weather Direct Mobile — Phase 1 Architecture

This document records the architecture found in the existing project before the isolated mobile prototype was built. The prototype is additive under `public/mobile/`; it does not replace the homepage, alter production navigation, or add a second publishing workflow.

## Target shape

```text
Weather/Data Sources
        ↓
Existing serverless APIs + shared browser intelligence modules
        ↓
avlweather.com pages + /mobile prototype
```

## Shared-code recommendations

1. Add a versioned `/api/router?route=mobile/bootstrap` (or product-bootstrap) response that aggregates current observation, hourly/daily weather, active alert, active Forecast Update, fresh Pulse, manual forecast metadata, and latest article. Keep individual routes for existing pages. This lowers cold starts and mobile request overhead without creating new publishing paths.
2. Persist Forecast Update as a distinct typed object during the existing forecast publish action: `{ active, title, message, publishedAt, expiresAt }`. Store it in the forecast payload or a dedicated KV key, but keep one admin action.
3. Extract Sunset Radiance's pure calculation functions from the inline HTML into an importable module. Have the current page and mobile/native data layer call the same function before displaying a score.
4. Move HikerScore calculation from `scripts/update-hiking-guidance.mjs` into `lib/hiking/score.js`; keep the generated JSON artifact as the lightweight public contract.
5. Consolidate weather normalization. `lib/api-routes/weather.js`, `public/js/weather-fetch.js`, `public/js/adapters/weather-adapter.js`, and page-local normalizers currently overlap, and `weather-fetch.js` drops `daily` and `airQuality` from its normalized return. Define a versioned contract with explicit units.
6. Add a server-side regional FEELSCORE batch route that applies the shared score engine once per location and returns score, category, emoji, observed/forecast timestamp, and engine version.
7. Normalize Pulse types. The current title is generally `Weather Pulse`; add an optional `kind` such as `radar`, `quick`, `camera`, or `forecast-note` so mobile can show labels like “RADAR UPDATE” without inferring meaning from prose.
8. Harden and cache the Substack adapter: return one stable shape, cache 15–30 minutes at the edge, allow only the known Substack host in `substack-og`, and prefer RSS enclosure/media fields before the HTML fallback.

## Mobile prototype behavior

- `Home`: active 828 alert and Forecast Update disappear when absent; current conditions; shared FEELSCORE; fresh Pulse; next six hours; four-day preview; Substack editorial card; Hiking and Sunset context.
- `Forecast`: the same manually published forecast object, with automated weather only as a missing-day fallback.
- `FEELSCORE`: Today/Tomorrow comfort windows, shared narrative and hourly score engines, and a lazy focused regional contour map.
- `Pulse`: full chronological feed. Only the Home placement honors the shared three-hour shelf life.
- `More`: simplified Hiking artifact view, a safe Sunset context view linking to the authoritative Radiance score, and permanent latest Substack article access.

For deterministic UI-state review, append `?preview=states` to the local mobile URL. This visibly labels and injects sample Alert and Forecast Update content while leaving all other data live.

## Native wrapper readiness

The prototype is compatible with a future Capacitor-style wrapper because it is a single responsive web surface using browser-native modules and APIs. Before packaging, complete these items:

- expose versioned, CORS-controlled HTTPS data contracts rather than relying on same-origin relative paths;
- extract Sunset and Hiking score logic into shared pure modules or server-owned results;
- add an aggregated bootstrap endpoint, request deduplication, offline/last-good metadata, and stale-data labels;
- define deep links for all six destinations and Substack/article handoff behavior;
- supply native icons, splash assets, safe-area/device testing and accessibility review;
- decide whether media opens in an in-app browser or system browser;
- add native notification token registration later, while keeping alerts published through the existing alert workflow;
- create separate development/staging API origins before any App Store or Play Store packaging.

No native package, account, payment, personalization, or native push implementation is part of Phase 1.
